Magic WAND UI/UX 규정
정리일: 2026-05-21

목적
================================================================================
이 문서는 Magic WAND 프로그램의 화면을 같은 기준으로 만들기 위한 UI/UX 규정이다.
현재 프로젝트는 ERP 웹사이트가 아니라 Windows용 Electron 데스크톱 앱이다.

Magic WAND의 첫 목표는 HomeLAB 환경에서 IP 주소, PC 네트워크 정보, 기본 진단을
한눈에 확인하고 관리하는 것이다. 이후 기능이 늘어나더라도 화면은 업무 도구처럼
차분하고, 버튼과 정보는 생활 속 표지판처럼 바로 이해되어야 한다.


0. 적용 범위와 우선순위
================================================================================

0-1. 적용 범위
--------------------------------------------------------------------------------
- 현재 활성 앱: Electron + HTML/CSS/JavaScript
- 주 화면 파일:
  - `renderer/index.html`: 화면 뼈대
  - `renderer/styles.css`: 화면 디자인
  - `renderer/app.js`: 화면 동작과 표시 문구
- `src/magic_wand/`의 Python/PySide6 코드는 이전 버전 참고용이다.
  새 UI 규칙을 적용할 주 대상은 Electron 화면이다.

0-2. 문서 우선순위
--------------------------------------------------------------------------------
UI/UX 판단 순서는 아래와 같다.

1. `AGENTS.md` / `CLAUDE.md`의 전역 작업 지침
2. `Rule_Project_Etc.txt`의 프로젝트 구조 설명
3. `Rule_UIUX.txt`
4. 기존 화면 구현 방식

호칭, 보안, 터미널 안전 규칙은 `AGENTS.md` / `CLAUDE.md`를 우선한다.
화면 구조와 파일 위치는 `Rule_Project_Etc.txt`를 우선한다.

0-3. 현재 앱 기준
--------------------------------------------------------------------------------
- 앱은 브라우저 웹사이트가 아니라 Electron 데스크톱 창으로 실행한다.
- 기본 창은 진짜 전체화면이 아니라 일반 창을 최대화해서 시작한다.
  즉, 상단 메뉴바와 Windows 창 버튼은 유지한다.
- 현재 공식 테마는 라이트 테마 1개다.
  다크 테마 규칙은 실제 구현을 시작할 때 별도 항목으로 추가한다.
- 현재 공식 앱 글꼴은 `NanumHuman`만 사용한다.
  다른 화면 글꼴이나 예비 글꼴을 추가하지 않는다.
- 앱 전체 줄간격은 `1.4`로 고정한다.
- 현재 메뉴 구조는 왼쪽 사이드메뉴의 `PC 관리`, `증빙 관리`, `프로그램 종료`를 기준으로 한다.
- 첫 단계 데이터 저장은 DB가 아니라 `data/ip_records.json` 파일을 사용한다.


1. 최상위 원칙
================================================================================

1-1. 화면 원칙
--------------------------------------------------------------------------------
- 간결하고 깔끔해야 한다.
- 같은 기능은 같은 모양이어야 한다.
- 색상은 적게 쓰고 의미는 분명해야 한다.
- 중요한 정보는 흐리게 숨기지 않는다.
- 반복 작업을 빠르게 할 수 있어야 한다.
- 장식보다 입력칸, 표, 상태 정보, 버튼이 먼저 잘 보여야 한다.
- 네트워크 전문 용어는 가능한 한 쉬운 한국어와 함께 쓴다.

예:
- `Gateway`만 쓰지 말고 `공유기 주소(게이트웨이)`처럼 적는다.
- `Private IP`만 쓰지 말고 `내 PC 사설 IP`처럼 적는다.
- 오류 메시지는 원인과 다음 행동을 짧게 알려준다.

1-2. 한 화면 안에서 일 처리 완료
--------------------------------------------------------------------------------
IP 관리 화면은 "왼쪽에서 등록/수정하고, 오른쪽에서 확인한다"는 구조를 유지한다.

- 왼쪽: IP 등록/수정 폼
- 오른쪽 위: 현재 네트워크 상태
- 오른쪽 중간: PC IP 정보, 장애 진단, IP 사용 현황
- 오른쪽 아래: 등록된 IP 목록과 검색

원칙:
- 데스크톱 기준 1080px x 720px 이상에서 주요 정보와 버튼이 함께 보여야 한다.
- 페이지 전체가 길게 늘어지는 것보다, 필요한 패널 안에서 스크롤되는 방식을 우선한다.
- 표, IP 주소 격자, 장비 목록처럼 데이터가 많아지는 영역은 내부 스크롤을 허용한다.
- 화면을 새로 만들 때도 "정보 확인 -> 선택 -> 실행" 흐름이 한 화면 안에서 이어지게 한다.

1-3. 색상은 적게, 의미는 분명하게
--------------------------------------------------------------------------------
한 화면에서 눈에 띄는 색상군은 4가지를 넘지 않는다.

1. 바탕색: 앱 배경, 패널 배경, 입력칸 배경
2. 글자/선색: 본문 글자, 설명 글자, 테두리
3. 핵심 액션색: 등록, 저장, 새로고침, 실행 같은 주요 동작
4. 상태색: 정상, 주의, 문제, 삭제 같은 상태 표현

색상이 더 필요해 보이면 색을 추가하기보다 문구, 위치, 굵기, 아이콘, 정렬로 구분한다.

1-4. 접근성 기본
--------------------------------------------------------------------------------
- 모든 버튼, 입력칸, 선택 목록은 Tab 키로 이동할 수 있어야 한다.
- `outline: none`으로 키보드 포커스 표시를 지우지 않는다.
- 아이콘만 있는 버튼을 만들 경우 `aria-label`을 반드시 넣는다.
- 버튼 글자와 배경은 충분히 구분되어야 한다.
- 색상만으로 상태를 구분하지 않는다. `정상`, `주의`, `문제` 같은 글자를 함께 보여준다.

1-5. 한국어 인코딩과 글자 깨짐 방지
--------------------------------------------------------------------------------
한국어 문구가 깨지면 사용자는 기능이 고장났다고 느낀다.

- 한글이 들어간 `.txt` 규정 문서는 UTF-8 BOM으로 저장한다.
  - 이유: Windows PowerShell 5.1 같은 도구는 BOM이 없으면 UTF-8 파일을 다른 문자표로 착각할 수 있다.
  - BOM은 파일 맨 앞에 붙는 작은 이름표 같은 것이다. 이 이름표가 있으면 Windows 도구가 "이 파일은 UTF-8"이라고 더 잘 알아본다.
- `Rule_UIUX.txt`, `Rule_Project_Etc.txt`, `Rule_PW.txt`는 모두 UTF-8 BOM으로 저장한다.
- `Rule_PW.txt`는 내용을 화면에 출력하지 말고, 인코딩 확인도 파일 앞 바이트와 UTF-8 유효성만 확인한다.
- 나중에 `Rule_PW.txt`의 토큰을 프로그램에서 직접 읽어 쓰게 되면, 읽은 문자열 맨 앞의 BOM 문자를 제거한 뒤 사용한다.
  - 이유: BOM은 파일 형식을 알려주는 이름표지만, 토큰 값에 섞이면 보이지 않는 글자가 비밀번호 앞에 붙은 것처럼 처리될 수 있다.
- HTML, CSS, JS, JSON, MD, PY 파일은 UTF-8로 저장한다.
- `renderer/index.html`에는 `<meta charset="UTF-8" />`를 유지한다.
- PowerShell에서 한글 파일을 읽을 때는 아래처럼 인코딩을 지정한다.

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
Get-Content -Raw -Encoding UTF8 -LiteralPath 'Rule_UIUX.txt'
```

- PowerShell에서 한글 `.txt` 파일을 저장할 때는 `-Encoding UTF8`을 명시한다.
  현재 프로젝트의 PowerShell 5.1에서는 이 방식이 UTF-8 BOM으로 저장된다.
- 터미널에 글자가 깨져 보인다고 해서 파일 자체가 깨졌다고 바로 판단하지 않는다.
  먼저 `Get-Content -Encoding UTF8`로 다시 읽어 실제 파일 내용을 확인한다.
- 한국어 문구를 수정한 뒤에는 실제 실행 화면 또는 UTF-8 읽기 명령으로 글자가 깨지지 않는지 확인한다.
- 깨진 문구를 발견하면 디자인 수정과 별개로 우선 고친다.


2. 색상 규정
================================================================================

2-1. 공식 색상 변수
--------------------------------------------------------------------------------
새 스타일은 가능한 한 `renderer/styles.css`의 CSS 변수를 사용한다.
직접 hex 색상을 계속 추가하면 냉장고에 같은 양념통이 이름만 다르게 늘어나는 것처럼
나중에 관리가 어려워진다.

현재 공식 변수:

역할                변수                 현재 값
전체 배경           `--bg`                #edf2f7
패널 배경           `--surface`           #ffffff
부드러운 배경       `--surface-soft`      #f7fafc
사이드 메뉴         `--nav`               #102033
사이드 메뉴 보조    `--nav-soft`          #172a42
공통 선             `--line`              #ccd6e2
본문 글자           `--text`              #17202a
보조 글자           `--muted`             #64748b
핵심 액션           `--blue`              #2563eb
핵심 액션 배경      `--blue-soft`         #e8f0ff
정상                `--green`             #15803d
정상 배경           `--green-soft`        #e8f6ee
주의                `--amber`             #b45309
주의 배경           `--amber-soft`        #fff2d8
위험                `--red`               #b42318
위험 배경           `--red-soft`          #fdecea

2-2. 색상 사용 원칙
--------------------------------------------------------------------------------
- 핵심 액션은 `--blue`를 기본으로 한다.
- 정상 상태는 `--green`, 주의 상태는 `--amber`, 위험 상태는 `--red`를 사용한다.
- 같은 의미에 여러 색을 섞지 않는다.
- 원색과 형광색은 기본 UI에 사용하지 않는다.
- 새 색이 필요하면 먼저 기존 변수로 표현할 수 있는지 확인한다.
- 정말 새 색이 필요하면 `:root`에 변수로 추가하고 용도를 주석이나 문서에 남긴다.

금지 예:
- #ff0000, #0000ff, #00ff00 같은 강한 원색
- 네온 느낌의 형광색
- 비슷한 파랑, 초록, 빨강을 화면마다 새로 만드는 방식

2-3. 상태색 기준
--------------------------------------------------------------------------------
상태는 색과 문구를 함께 사용한다.

상태      색상 변수        사용 예
정상      `--green`        정상, 사용 중, 응답 있음
주의      `--amber`        확인 필요, 게이트웨이, 일부 실패
위험      `--red`          오류, 삭제, 진단 실패
중립      `--muted`        비활성, 정보 없음, 확인 전

IP 주소 격자 기준:
- 비어 있음: 중립 색상
- 사용 중: 정상 색상
- 현재 PC: 핵심 액션색
- 공유기/게이트웨이: 주의 색상


3. 레이아웃 규정
================================================================================

3-1. 앱 전체 구조
--------------------------------------------------------------------------------
기본 구조는 아래 형태를 유지한다.

- `.app-shell`: 왼쪽 메뉴 + 오른쪽 작업 영역
- `.side-menu`: 메뉴 그룹, 하위 메뉴 버튼, 프로그램 종료 버튼
- `.main-content`: 실제 기능 화면
- `.page-grid`: 왼쪽 입력 패널 + 오른쪽 작업 패널

기본 기준:
- 왼쪽 메뉴 폭은 200px 기준으로 유지한다.
- 사이드메뉴 위/아래 여백은 각각 12px, 좌우 여백은 각각 8px로 둔다.
- 사이드메뉴 안쪽 메뉴 버튼 공간은 184px 기준으로 유지한다.
- 사이드메뉴 버튼은 최소 높이 32px, 좌우 내부 여백 8px, radius 6px 기준으로 한다.
- 사이드메뉴 항목 사이 간격은 4px 기준으로 한다.
- 추후 개발 예정 사이드메뉴 항목은 클릭 시 `개발 중입니다` 안내 페이지를 보여준다.
- IP 등록 패널 폭은 320px 기준으로 유지한다.
- 박스, 패널, 도표, 버튼 묶음처럼 화면 요소 사이 간격은 6px 기준으로 한다.
- 카드/패널 radius는 8px 기준으로 한다.
- 메인 페이지 자체가 아래로 스크롤되면 안 된다.
- 각 메인 페이지는 `개발 중입니다` 페이지처럼 화면에 딱 맞는 기본 박스/패널 안에 내용을 배치한다.
- 세로 스크롤은 필요할 때만 박스/패널 내부 영역에서 사용한다.
- 목록, 표, 긴 점검 결과처럼 길어질 수 있는 영역은 미리 고정된 공간을 확보하고, 그 내부에서만 스크롤되게 한다.
- PC 사양처럼 텍스트로 전달하기 좋은 정보는 카드 여러 개보다 복사하기 쉬운 트리형 텍스트 박스를 우선한다.
- 기본 업무 화면에서는 그림자를 사용하지 않는다.
- 너무 둥근 카드나 과한 장식은 사용하지 않는다.

3-2. 패널 사용
--------------------------------------------------------------------------------
패널은 "기능을 묶는 상자"다.

허용:
- IP 등록 폼
- 네트워크 상태 요약
- PC IP 정보
- 진단 결과
- IP 사용 현황
- IP 목록

금지:
- 패널 안에 별 의미 없는 장식용 패널을 다시 넣는 구조
- 클릭할 때마다 카드가 크게 움직이는 hover 효과
- 정보보다 장식이 먼저 보이는 과한 효과

3-3. 표와 목록
--------------------------------------------------------------------------------
- IP 목록은 표 형태를 유지한다.
- 표 헤더는 스크롤 중에도 보이도록 sticky 처리를 유지한다.
- 행 높이는 42px 안팎으로 유지한다.
- 긴 메모는 줄바꿈되게 하되, 표 전체가 무너지지 않게 한다.
- 선택된 행은 배경색으로 표시하되 글자도 충분히 읽혀야 한다.
- 빈 목록은 `등록된 IP가 없습니다.`처럼 짧고 분명하게 안내한다.

3-4. IP 주소 격자
--------------------------------------------------------------------------------
IP 사용 현황의 주소 격자는 작은 버튼들의 모음이다.

- 각 칸은 최소 36px 높이를 유지한다.
- 끝자리 숫자가 잘 보여야 한다.
- 클릭하면 해당 IP를 입력칸에 채우는 동작을 유지한다.
- 마우스를 올렸을 때 title 또는 툴팁으로 IP, 사용 여부, 장비명을 확인할 수 있게 한다.


4. 버튼 규정
================================================================================

4-1. 버튼 의미
--------------------------------------------------------------------------------
색상 배경 버튼은 화면 결과를 크게 바꾸는 핵심 동작에만 사용한다.

핵심 버튼 예:
- 등록
- 저장
- 새로고침
- 진단 실행
- IP 대역 스캔

보조 버튼 예:
- 수정
- 비우기
- 검색
- 선택

위험 버튼 예:
- 삭제
- 프로그램 종료

4-2. 버튼 모양
--------------------------------------------------------------------------------
- 일반 버튼 높이는 38~40px 범위를 유지한다.
- 버튼 radius는 8px 기준으로 현재 앱 스타일과 맞춘다.
- 같은 묶음 안의 버튼은 높이와 여백을 맞춘다.
- 비활성 버튼은 흐리게 보이되 글자는 읽을 수 있어야 한다.
- hover 상태에서도 글자와 배경이 섞이면 안 된다.

4-3. 버튼 문구 표준
--------------------------------------------------------------------------------
같은 행동에는 같은 단어를 쓴다.

행동                  문구
새 항목 만들기        등록
선택 항목 수정        수정
수정 내용 저장        저장
선택 항목 삭제        삭제
입력칸 초기화         비우기
네트워크 정보 갱신    현재 정보 새로고침
진단 시작             진단 실행
IP 사용 현황 조사     IP 대역 스캔
앱 닫기               프로그램 종료

토스트 문구:
- 성공: `등록 완료`, `수정 완료`, `삭제 완료`
- 실패: `등록 실패`, `수정 실패`, `삭제 실패`
- 안내: `수정할 IP를 목록에서 선택해 주세요.`


5. 글자와 문구 규정
================================================================================

5-1. 글꼴
--------------------------------------------------------------------------------
현재 앱 기본 글꼴은 `NanumHuman`만 사용한다.

금지:
- 화면별로 새로운 웹폰트를 추가하는 방식
- `NanumHuman` 외 다른 글꼴이나 예비 글꼴을 추가하는 방식
- 장식용 글꼴 사용
- `style=`로 font-family를 직접 지정하는 방식

5-2. 글자 크기와 두께
--------------------------------------------------------------------------------
굵기 기준:
- Regular: `400`
- Bold: `700`
- ExtraBold: `800`

기본:
- 기본 글자 크기: `12px`
- 기본 줄간격: `1.4`

사이드메뉴:
- 그룹 제목: `12px`, Bold
- 하위 항목: `12px`, Regular

메인 페이지:
- 섹션 라벨: `12px`, Bold
- 검색 라벨: `12px`, Regular
- 표 제목: `12px`, Bold
- 개발 예정 안내 문구: `24px`, ExtraBold

별도 모달 창:
- 종료 확인창 제목: `12px`, Bold

기타:
- PC 사양 트리 텍스트: `12px`, Regular
- 안내 배너: `12px`, Regular
- 라디오 선택 항목: `12px`, Regular

5-3. 문구 톤
--------------------------------------------------------------------------------
재훈 님이 네트워크 전문가가 아니어도 바로 이해할 수 있게 쓴다.

원칙:
- 짧고 분명하게 쓴다.
- 전문 용어는 쉬운 말과 함께 쓴다.
- 실패 메시지는 사용자가 다음에 무엇을 하면 되는지 알려준다.
- 같은 뜻의 단어를 섞지 않는다. 예: `등록`과 `추가`를 같은 의미로 혼용하지 않는다.

예:
- 나쁨: `Scan failed`
- 좋음: `IP 대역 스캔 실패: 네트워크 연결을 확인해 주세요.`


6. 입력칸과 폼 규정
================================================================================

6-1. IP 등록 폼
--------------------------------------------------------------------------------
IP 등록 폼은 왼쪽 패널에 유지한다.

필드 기본 순서:
1. 이름
2. IP 주소
3. 장소
4. 메모

원칙:
- 이름과 IP 주소는 필수 입력으로 유지한다.
- IP 주소는 IPv4 형식인지 확인한다.
- 저장 전 오류는 토스트로 알려주고, 문제가 있는 입력칸에 focus를 준다.
- placeholder는 예시를 보여주되 실제 값처럼 오해되지 않게 한다.

6-2. 검색
--------------------------------------------------------------------------------
- 검색은 IP 목록 영역 안에 둔다.
- 검색 대상은 이름, IP 주소, 장소, 메모다.
- 검색 입력 중 즉시 목록이 줄어드는 현재 방식을 유지한다.
- 검색 결과가 없으면 빈 상태 문구를 보여준다.


7. 상호작용 규정
================================================================================

7-1. 선택과 수정 흐름
--------------------------------------------------------------------------------
IP 목록에서 행을 클릭하면 왼쪽 폼에 값이 채워진다.

원칙:
- 선택된 행은 눈에 띄게 표시한다.
- 선택 전에는 수정/삭제 버튼을 비활성화한다.
- `비우기`를 누르면 선택 상태와 입력값이 함께 초기화된다.

7-2. 오래 걸리는 작업
--------------------------------------------------------------------------------
네트워크 조사, IP 대역 스캔, 진단 실행은 시간이 걸릴 수 있다.

원칙:
- 작업 중에는 해당 버튼을 비활성화한다.
- 상태 문구를 `확인 중`, `진단 중`, `스캔 중`처럼 바꾼다.
- 완료 또는 실패 후 버튼을 다시 활성화한다.
- 실패하면 기술적인 오류만 던지지 말고 사용자가 이해할 문구를 함께 보여준다.

7-3. 토스트
--------------------------------------------------------------------------------
토스트는 화면 아래 중앙에 짧게 표시한다.

- 성공/실패/안내 문구를 짧게 보여준다.
- 너무 긴 설명은 토스트에 넣지 않는다.
- 같은 작업이 반복되면 기존 토스트를 새 문구로 교체한다.
- 중요한 삭제 확인은 토스트가 아니라 확인 창을 사용한다.


8. 코드 작성 규정
================================================================================

8-1. CSS 작성
--------------------------------------------------------------------------------
- 공통 스타일은 `renderer/styles.css`에 둔다.
- 새 색상은 먼저 기존 CSS 변수를 사용한다.
- 같은 선택자를 파일 아래쪽에 다시 만들어 덮어쓰는 방식은 피한다.
- `!important`는 외부 라이브러리 스타일을 어쩔 수 없이 이길 때만 사용한다.
- 버튼, 입력칸, 패널처럼 공통 요소는 한 곳에서 관리한다.

8-2. HTML 작성
--------------------------------------------------------------------------------
- 화면 구조는 `renderer/index.html`에 둔다.
- 새 `<style>` 태그는 만들지 않는다.
- 버튼에는 `type="button"` 또는 `type="submit"`을 명확히 둔다.
- 화면에 보이는 한국어 문구는 깨지지 않게 UTF-8로 저장한다.
- `aria-label`, `aria-expanded`, `aria-controls` 같은 접근성 속성은 실제 상태와 맞춘다.

8-3. JavaScript 작성
--------------------------------------------------------------------------------
- `renderer/app.js`는 화면 동작과 상태 표시를 담당한다.
- JavaScript에서 색상 hex를 직접 넣지 않는다.
- 상태에 따라 색이 필요하면 class 이름을 붙이고 CSS에서 처리한다.
- 사용자에게 보이는 문구는 한국어로 통일한다.
- 오류 문구는 원문 오류를 그대로 던지기보다 짧은 안내와 함께 보여준다.

8-4. 현재 프로젝트에 없는 규칙
--------------------------------------------------------------------------------
현재는 Electron 데스크톱 앱에 필요한 규칙만 둔다.
웹 서버, 권한 관리, 인쇄, 대형 대시보드처럼 아직 구현하지 않는 기능의
세부 UI 규칙은 미리 넣지 않는다.

필요해지는 시점이 오면 그때 실제 구조에 맞게 새 항목으로 추가한다.
